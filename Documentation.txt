--------------------------------------------------------------------
PROJECT OVERVIEW
--------------------------------------------------------------------
Name: KeyPoints Studio
Goal: Upload a recorded meeting (audio/video) and automatically
      generate a structured, editable Minutes of Meeting (MOM),
      exportable as PDF/DOCX.

Type: Upload-based system (NOT a live meeting assistant in V1).

Pipeline:
  Meeting Recording -> Audio Processing -> Speech-to-Text ->
  Transcript -> AI/NLP Analysis -> Structured MOM ->
  Editable MOM -> PDF/DOCX Export

Full tech stack, architecture principles, and long-term plan are
defined in the original master prompt. Key decisions from it:
  - Frontend: React + Vite + Tailwind CSS
  - Backend: FastAPI (Python 3.11)
  - Speech-to-Text: Whisper (or faster-whisper), swappable
  - LLM: Gemini API (or OpenAI/Claude/Ollama), swappable
  - Documents: ReportLab (PDF), python-docx (DOCX)
  - Database: SQLite for dev, PostgreSQL for later/production
  - Diarization, Auth, Deployment are explicitly LATER phases
  - Service-abstraction pattern: no tight coupling to one AI
    provider (TranscriptionService, LLMService interfaces)
  - Development machine: Windows 11, Intel i3 12th gen, no
    guaranteed GPU -> everything must run on CPU for MVP

Development must proceed in strict phases (see master prompt,
Section 14). Do NOT skip ahead or build multiple phases in one go.

  │   └── main.py                 (UPDATED: registers meetings router,

  ├── storage/
  │   └── uploads/                (NEW: created automatically on
  │                                 startup via config.py, not
  │                                 committed to git)
  └── requirements.txt            (UPDATED: added python-multipart)

What it does:
  - POST /api/meetings/upload accepts a multipart/form-data file.
  - Validates file extension against {.mp3, .wav, .m4a, .mp4}.
  - Streams the file to disk in 1MB chunks (keeps memory usage low
    for long recordings on a machine without much RAM to spare).
  - Rejects files over 500MB (partial file is deleted on rejection).
  - Rejects empty files.
  - Generates a UUID as the meeting_id and saves the file as
    backend/storage/uploads/{meeting_id}{extension}.
  - Returns JSON: meeting_id, original_filename, saved_filename,
    size_bytes, status.
  - No database persistence yet - the meeting_id + saved file on
    disk is the only record for now. Database arrives in Phase 9.

Why it was built this way:
  - Chunked streaming (instead of file.read() all at once) avoids
    loading an entire 2-hour recording into RAM on the dev's i3
    laptop with limited resources.
  - Validation happens before/during save, not after, so we never
    keep invalid or oversized files sitting on disk.
  - config.py centralizes storage path + allowed types + size limit
    so later phases (FFmpeg, Whisper, MOM export) reuse the same
    constants instead of redefining them inconsistently.
  - meeting_id (UUID) generated now, ahead of the database, so the
    API contract (what the frontend receives and later sends back
    to /transcribe, /generate-mom, etc.) doesn't need to change once
    Phase 9 adds persistence - we just start writing this ID to a
    database row instead of only using it as a filename.

How to run/test it (Windows):
  1. cd mom-generator/backend
  2. venv\Scripts\activate   (create venv first if not done - see
     Phase 1 log above)
  3. pip install -r requirements.txt   (installs python-multipart)

     (Swagger UI) and try the /api/meetings/upload endpoint there -
     easier than curl on Windows.
  Expected result: JSON response with a meeting_id, and the file
  appears inside backend/storage/uploads/.

[PHASE 3] — FFmpeg
Status: COMPLETE (awaiting user confirmation before Phase 4)
Date: 2026-08-08

What was built:
  backend/
  ├── app/
  │   ├── core/
  │   │   └── config.py              (UPDATED: added PROCESSED_DIR,
  │   │                                created on import like UPLOAD_DIR)
  │   └── services/
  │       ├── __init__.py            (NEW)
  │       └── audio_service.py       (NEW: check_ffmpeg_installed(),
  │                                    convert_to_wav())
  ├── storage/
  │   └── processed/                 (NEW: converted WAV files land
  │                                    here, not committed to git)
  └── scripts/
      └── test_audio_service.py      (NEW: standalone CLI test,
                                       no API/server required)

What it does:
  - check_ffmpeg_installed() uses shutil.which("ffmpeg") to detect
    whether the FFmpeg executable is on the system PATH. This is
    checked BEFORE attempting conversion, so failures are clear
    ("FFmpeg is not installed...") rather than a cryptic subprocess
    crash.
  - convert_to_wav(meeting_id, input_path) runs:
      ffmpeg -y -i <input> -ar 16000 -ac 1 -c:a pcm_s16le <output>
    producing a 16kHz, mono, 16-bit PCM WAV file - the format
    Whisper (Phase 4) is built to expect.
  - Output is saved to backend/storage/processed/{meeting_id}.wav
  - On failure, the last few lines of FFmpeg's stderr are surfaced
    in the raised AudioProcessingError (FFmpeg's own errors are
    usually the most useful part of a long noisy log).
  - scripts/test_audio_service.py lets the developer test this
    entire flow from the command line without starting the FastAPI
    server - it finds the most recent file in storage/uploads/ (or
    accepts an explicit path) and converts it, printing success or
    a clear failure reason.

Why it was built this way:
  - STACK DEVIATION (flagged per Rule 4): the master prompt listed
    `ffmpeg-python` as a dependency. We used Python's built-in
    `subprocess` module directly instead, and did NOT add
    ffmpeg-python to requirements.txt. Reason: ffmpeg-python is a
    thin wrapper that ultimately shells out to the ffmpeg binary
    anyway; calling subprocess directly gives clearer access to
    FFmpeg's real stderr output for debugging, and avoids adding a
    dependency that isn't pulling real weight yet (Rule 5). This
    can be revisited if a future phase needs more complex FFmpeg
    pipelines (e.g. filter graphs for chunking in Phase on long
    audio handling).
  - No new API endpoint was added in this phase. The master prompt
    explicitly says to "test independently" in Phase 3 - FFmpeg
    conversion will be wired into the pipeline when Phase 4
    (Whisper) calls it automatically before transcribing.
  - 16kHz / mono / 16-bit PCM was chosen because it's the standard
    input format Whisper's own documentation recommends - matching
    it exactly avoids Whisper doing its own (slower, CPU-costly)
    resampling internally.

How to run/test it (Windows):
  Prerequisite - install FFmpeg itself (separate from any pip
  package):
    winget install Gyan.FFmpeg
    (or download manually from https://ffmpeg.org/download.html
    and add its bin/ folder to your system PATH)
  Then close and reopen your terminal, and verify with:
    ffmpeg -version

  Then, from backend/ with venv activated:
    python scripts/test_audio_service.py
  (This automatically picks the most recent file in
  storage/uploads/ - the one you uploaded during Phase 2 testing.
  Or pass a specific path as an argument.)

  Expected output:
    Checking for FFmpeg on your system PATH...
    FFmpeg found.
    ...
    Conversion SUCCEEDED.
    Output file: ...\storage\processed\{id}.wav
    Size: ... KB
    Format: 16kHz, mono, 16-bit PCM WAV

  Then confirm the .wav file exists in backend\storage\processed\.

  - (To be confirmed by developer after running the steps above.)

Known issues / things to watch:
  - FFmpeg must be manually installed on each machine this runs on

    setup snag and is checked explicitly with a clear error message
    rather than failing silently.
  - No audio chunking yet for very long recordings - that's Phase

  │                                             faster-whisper)
  └── scripts/
      └── test_transcription_service.py       (NEW: standalone CLI test)

What it does:
  - TranscriptionService is an abstract base class (ABC) defining one
    method: transcribe(audio_path) -> {"text": str, "segments": [...]}
  - FasterWhisperService is the concrete implementation, using the
    faster-whisper library with model_size="base", device="cpu",
    compute_type="int8" (a speed/accuracy tradeoff suited to CPU-only
    hardware).
  - get_transcription_service() is a factory function - the ONE place
    that decides which provider is active. Any future caller imports
    this function, never FasterWhisperService directly, so swapping
    providers later means changing one function body, not every call
    site.
  - scripts/test_transcription_service.py finds the most recent .wav
    in storage/processed/ (or accepts an explicit path), loads the
    model, transcribes it, and prints the full text plus the first 5
    timestamped segments.

Why it was built this way:
  - STACK DEVIATION (flagged per Rule 4): chose faster-whisper over
    plain openai-whisper as the implementation, even though the
    master prompt lists Whisper as primary. Justification: the
    target machine is confirmed CPU-only (Intel i3, no guaranteed
    GPU) - exactly the condition under which the master prompt says
    to "consider faster-whisper if CPU performance becomes an
    issue." faster-whisper uses the CTranslate2 inference engine and
    is meaningfully faster on CPU with comparable transcript quality.
  - Abstract base class used (not just a plain function) specifically
    to satisfy the master prompt's "service abstraction" architecture
    principle - the same pattern will apply to llm_service.py in
    Phase 6.
  - No new API endpoint yet, consistent with the Phase 3 precedent:
    build and verify the service standalone first via script, wire
    it into a real HTTP endpoint (POST /api/meetings/{id}/transcribe)
    when Phase 5's Transcript UI actually needs to call it.
  - model_size="base" chosen as a starting default (fast enough for
    short test clips on CPU, reasonable accuracy). This is a config
    constant specifically so it can be bumped to "small" or "medium"
    later without touching service code, if accuracy becomes an
    issue.

How to run/test it (Windows):
  From backend/ with venv activated:
    pip install -r requirements.txt   (installs faster-whisper - this
                                        may take a few minutes, it has
                                        several dependencies)
    python scripts/test_transcription_service.py

  IMPORTANT - first run behavior:
    - faster-whisper downloads the "base" model (~140MB) from the
      internet automatically on first use. This is a ONE-TIME
      download, cached locally afterward.
    - Actual transcription also takes real CPU time - be patient,
      especially on the very first run.

  Expected output (abbreviated):
    Loading faster-whisper model (first run downloads it - be patient)...
    Model loaded.
    Transcribing: ...\storage\processed\{id}.wav
    Done in ... seconds.
    --- Full transcript text ---
    <your spoken content, transcribed>
    --- Segments (first 5) ---
    [  0.00s -   2.30s] <segment text>
    ...

[PHASE 4 ADDENDUM] — Language detection fix
Date: 2026-08-08

What happened:
  - Developer tested with a real Hindi speech recording. Whisper's
    "base" model auto-detected the language incorrectly and produced
    fluent-sounding but nonsensical English text instead of an
    accurate Hindi transcript (or transliteration). This is a known
    weak point of the "base" model - a small/multilingual model is
    more accurate but slower on CPU.

What was changed:
  - transcription_service.py: transcribe() now accepts an optional
    `language` parameter (ISO 639-1 code, e.g. "hi", "en"). If not
    given, it falls back to WHISPER_LANGUAGE in config.py (default
    None = auto-detect).
  - TranscriptResult now also includes "detected_language" and
    "language_confidence" (0.0-1.0) so a garbled transcript can be
    diagnosed immediately - low confidence is a clear red flag
    rather than a silent failure.
  - config.py: added WHISPER_LANGUAGE setting (default None).
  - test_transcription_service.py: accepts an optional second CLI
    argument to force a language, and now prints the detected
    language + confidence, with a warning if confidence is low.

Why:
  - This project's real-world use case (Indian meetings, per the
    developer's context) will very often involve Hindi, English, or
    mixed Hindi/English speech. Silently mis-detecting language and
    producing confident-sounding wrong text is exactly the kind of
    hallucination the master prompt's Section 9 (Hallucination
    Control) warns against, even though that section specifically
    discusses the LLM/MOM stage - the same principle (never let the
    system state something with false confidence) applies here too.

How to use going forward:
  - If you know a meeting is primarily in Hindi:
      python scripts/test_transcription_service.py path\\to\\file.wav hi
  - If mostly English:
      python scripts/test_transcription_service.py path\\to\\file.wav en
  - Once this is wired into the API in Phase 5, the language will
    become a parameter the frontend can expose to the user (e.g. a
    dropdown), rather than something hardcoded.

[PHASE 5 - PART 1] — Transcript UI: backend endpoints
Status: COMPLETE (awaiting user confirmation before Part 2 / frontend)
Date: 2026-08-08

What was built:
  backend/app/
  ├── api/routes/meetings.py       (UPDATED: added
  │                                  POST /{meeting_id}/transcribe
  │                                  GET /{meeting_id}/transcript
  │                                  plus helper functions
  │                                  _find_uploaded_file() and
  │                                  _transcript_path())
  ├── services/transcription_service.py  (UPDATED: get_transcription_
  │                                        service() is now cached
  │                                        with @lru_cache(maxsize=1))
  └── main.py                      (UPDATED: health check phase label)

What it does:
  - POST /api/meetings/{meeting_id}/transcribe:
      1. Looks up the originally uploaded file by meeting_id
         (glob match on {meeting_id}.* in storage/uploads/)
      2. Runs audio_service.convert_to_wav() (Phase 3)
      3. Runs transcription_service (Phase 4), with an optional
         ?language=hi query parameter to force a language
      4. Saves the result to
         storage/processed/{meeting_id}_transcript.json
      5. Returns the transcript JSON in the response
  - GET /api/meetings/{meeting_id}/transcript:
      - Reads and returns the saved transcript JSON.
      - Returns a clean 404 with a helpful message if /transcribe
        hasn't been run yet for that meeting_id.
  - Both endpoints convert internal errors (FFmpeg failures, Whisper
    failures) into safe, non-technical HTTP error messages, per the
    project's error handling rules (Section 16) - no raw Python
    tracebacks are ever sent to the caller.
  - transcription_service.get_transcription_service() is now cached
    with lru_cache, so the ~500MB "small" Whisper model loads into
    memory ONCE per running server process, not on every request.
    Without this, every single /transcribe call would pay the full
    model-loading cost again, adding significant unnecessary delay.

Why it was built this way:
  - No database yet (Phase 9), so the transcript JSON file itself
    IS the persistence layer for now - meeting_id ties together the
    uploaded file, the processed WAV, and the transcript JSON, all
    living in predictable, meeting_id-based filenames. This will
    translate directly into database rows later without changing
    the API's external behavior.
  - Model caching (lru_cache) was added proactively rather than
    waiting for the developer to notice slow repeated requests -
    this is a correctness/performance concern that would otherwise
    surface confusingly later (e.g. "why is my second upload just
    as slow as my first?").
  - Both endpoints are defined as regular (non-async) route
    functions. FastAPI automatically runs synchronous route
    functions in a background thread pool, which is the correct
    approach for CPU-bound blocking work like FFmpeg and Whisper -
    it avoids blocking the server's event loop while a transcription
    is running.

How to run/test it (Windows):
  1. From backend/, with venv active: uvicorn app.main:app --reload
  2. Open http://127.0.0.1:8000/docs
  3. Use POST /api/meetings/{meeting_id}/transcribe:
     - Enter a meeting_id from a previous upload (Phase 2 test)
     - Optionally set language to "hi" or "en" as a query parameter
     - Execute - this may take several seconds depending on
       recording length and whether the model needs to (re)download
  4. Use GET /api/meetings/{meeting_id}/transcript with the same
     meeting_id - should return the same result instantly (no
     re-processing).
  5. Confirm storage/processed/{meeting_id}_transcript.json exists
     and contains the expected JSON.

What it does:
  - User drags/selects a file -> UploadCard validates the extension
    client-side (backend re-validates regardless) -> calls
    uploadMeeting()
  - On success, automatically calls transcribeMeeting() with the
    returned meeting_id (no language forced by default - relies on
    WHISPER_LANGUAGE / auto-detect from Phase 4, exactly as the
    backend already handles it)
  - While processing, shows a spinner with an honest message (no
    fake progress percentage, since the backend doesn't report
    partial progress)
  - On success, shows TranscriptView: detected language + confidence
    badge (with a visible low-confidence warning, matching the same
    diagnostic added to the backend in the Phase 4 addendum), then
    each segment with its timestamp
  - On failure at any step, shows the actual error message from the
    backend (which is already user-safe text, never a raw traceback,
    per Section 16 of the master prompt) with a "Try again" button
  - CORS middleware added to the backend - without this, every
    fetch() call from the browser would be silently blocked by the
    browser itself before even reaching FastAPI

Why it was built this way:
  - Design approach: grounded in what this actually is (a document-
    processing tool with a real 3-stage pipeline), not a generic
    marketing template. Colors/type deliberately avoid the common
    "cream + terracotta" AI-generated look - used a teal-green ink
    accent instead, paired with a serif display face (Source Serif
    4) for the "meeting minutes" document feel, Inter for UI chrome,
    and JetBrains Mono specifically for timestamps, since data
    should visually read as data.
  - PipelineStepper shows exactly 3 stages because that's what
    genuinely happens - resisted the temptation to fake finer-
    grained progress (e.g. "Converting..." then "Transcribing...")
    since the backend returns one combined result and doesn't
    stream intermediate status. Showing fake granularity would
    misrepresent what's actually occurring, which conflicts with
    the project's broader "don't invent things that aren't true"
    principle (echoing Section 9's hallucination-control spirit,
    applied to UI honesty rather than AI output).
  - api.js centralizes every backend call in one file - if the API
    base URL changes (e.g. moving to a deployed backend in Phase 12),
    or if auth headers need to be added later (Phase 11), there's
    exactly one file to touch.
  - No routing library (e.g. react-router) added yet - Rule 5 (avoid
    unnecessary libraries). This is currently a single-page flow; a
    router will make sense once there's a meetings list / dashboard
    (mentioned in the master prompt's later frontend plans).

What it does:
  - POST /generate-mom: reads the meeting's saved transcript.json
    (from Phase 5), calls llm_service.extract_mom() via
    mom_service.generate_mom(), saves the result to
    storage/processed/{meeting_id}_mom.json, returns it. Returns 404
    if no transcript exists yet, 400 if the transcript is empty.
  - GET /mom: reads and returns the saved MOM JSON. 404 if
    /generate-mom hasn't been run yet.
  - PUT /mom: accepts an edited MOM in the request body, typed as
    MOMResult - FastAPI automatically validates the edit against the
    same Pydantic schema used for AI-generated MOMs, so a malformed
    edit (e.g. an action item missing its "task" field) is rejected
    with a 422 error before ever reaching the route function. Saves
    the edit via the same save_mom() used for fresh generations.

Why it was built this way:
  - mom_service.py exists specifically so there is ONE function
    (save_mom) that defines what a MOM looks like on disk, used
    identically whether the MOM just came from the LLM or was just
    hand-edited by the user in the UI - no separate "generated MOM"
    vs "edited MOM" file formats to keep in sync.
  - Reusing the MOMResult Pydantic schema for the PUT request body
    (not a separate "MOMUpdateRequest" schema) means edits are held
    to the exact same validation as AI output - a person editing the
    MOM in the UI can't accidentally save something structurally
    invalid either.
  - Errors follow the same pattern as every other endpoint in this
    project: LLMExtractionError's already-safe message is passed
    through, but any other unexpected exception is caught and
    replaced with a generic, non-technical message (Section 16).

    the last SAVED version, not unsaved in-progress edits.

  - Chose ReportLab's Platypus (SimpleDocTemplate) over raw Canvas
    drawing specifically because Platypus handles text wrapping,
    page breaks, and table layout automatically - a MOM's summary or
    a long action item description could easily overflow a fixed
    canvas position, and Platypus reflows content instead of
    silently clipping or overlapping text.
  - document_service.py deliberately does NOT call the LLM or touch
    transcripts - it only ever reads an already-validated MOMResult
    object. This keeps a hard boundary between "AI-generated content"
    and "document rendering," so a rendering bug can never
    accidentally introduce hallucinated content, and an LLM change
    can never accidentally break document formatting.
  - Plain anchor tags (not a fetch+blob JS download) for the
    frontend buttons - simpler code, and it's the correct approach
    per Rule 5 (avoid unnecessary complexity): the backend already
    sends the right headers for the browser to handle this natively.

  │                                  pure merge_chunk_segments(); short audio is

  ├── services/api.js           (UPDATED: added getMeetingProgress())
  └── pages/HomePage.jsx        (UPDATED: polls /progress during processing and MOM
                                 generation and shows the backend-reported message +
                                 a real progress bar)

What it does:
  - Recordings longer than LONG_AUDIO_THRESHOLD_SECONDS (10 minutes) are no longer
    transcribed as one giant call. audio_service.split_audio() cuts the normalized WAV
    into fixed-duration chunks (5 minutes) with a 2s overlap so a word straddling a
    boundary isn't clipped; each chunk is transcribed separately and the results are
    merged with absolute timestamps, dropping the overlapping region so words aren't
    duplicated.
  - Because transcription now happens in discrete chunks (and conversion / MOM
    generation are also discrete stages), the backend records its ACTUAL progress in an
    in-memory store exposed via GET /api/meetings/{meeting_id}/progress. The frontend
    polls this endpoint and only ever shows what the backend genuinely reports.
  - Short recordings (<= 10 minutes) take the exact same single-pass path as before
    Phase 11 - behavior is unchanged for existing short test clips.

Why it was built this way:
  - "Safe chunking": the target machine (Intel i3, CPU-only) is the reason. A single
    very long transcription call on CPU is slow and memory-hungry; fixed chunks keep
    every model call bounded and give natural units for progress.
  - Honest progress (master prompt Section 9 spirit, applied to the UI): the docs
    explicitly avoided fake progress bars because "the backend doesn't report partial
    progress." Phase 11 fixes the root cause - the backend now DOES report real
    progress - so the UI can show a real bar/message without inventing anything.
  - Chunk files are deleted after transcription (finally block), matching the existing
    convention of not leaving scratch files in storage/.
  - progress.py is a lock-guarded process-local dict: transient status, not durable
    data, so it resets on restart - acceptable for development, swappable for a
    distributed store later without changing callers.

[PHASE 14] Speaker Diarization
--------------------------------------------------------------------
Status: COMPLETE
Date: 2026-08-24

What was built:
  NEW  backend/app/services/diarization_service.py
  MOD  backend/app/services/transcription_service.py
  MOD  backend/app/services/llm_service.py

  MOD  frontend/src/pages/HomePage.jsx
  MOD  frontend/src/components/TranscriptView.jsx

What it does:
  Adds optional speaker identification to the transcription pipeline.
  When the user enables the "Identify speakers" toggle before uploading,
  the backend runs a diarization step AFTER Whisper that:
    1. Reads each Whisper segment's audio window from the WAV file.
    2. Computes a 40-dimensional log-mel spectrogram embedding per segment
       (pre-emphasis → framing → Hann window → FFT → mel filterbank → log → mean).
    3. Normalizes embeddings with StandardScaler.
    4. Clusters them with AgglomerativeClustering (ward linkage), auto-detecting
       the number of speakers or using DIARIZATION_MAX_SPEAKERS as a cap.
    5. Assigns stable "Speaker N" labels sorted by first appearance.
  The transcript text is then reformatted as "Speaker N: sentence" lines,
  which both the LLM (for better participant attribution) and the frontend
  (for coloured rendering) consume.

  The frontend TranscriptView now supports three modes:
    - Diarized: speaker-coloured badges, grouped by speaker change (chat-style).
    - Segmented: plain timestamps (same as Phases 1-13).
    - Plain text: raw text fallback for old transcripts without segment data.

  GET /transcript now returns `segments` and `has_diarization` so the
  MeetingDetail view can render speaker-coloured transcripts for past meetings.

Why built this way:
  - MFCC + sklearn chosen over pyannote.audio (which needs torch ~2GB +
    a HuggingFace token) because the target machine is CPU-only Intel i3.
    scipy and scikit-learn are small, install cleanly on Windows, and add
    no GPU requirement.
  - Diarization is DISABLED by default (DIARIZATION_ENABLED=false in .env).
    When disabled, the entire transcription pipeline is byte-for-byte
    identical to Phase 13 — no new code paths run, no new packages load.
  - apply_diarization() is a pure post-processing step (never re-runs Whisper).
    It degrades gracefully: any failure logs a warning and returns the
    original transcript unchanged so diarization never breaks a recording.
  - The Transcript model gained two nullable columns (segments_json,
    has_diarization) so all existing rows continue to load without any
    data migration.
  - LLM rule 6 updated to explicitly leverage "Speaker N:" labels, improving
    participant attribution and speaker-specific action item extraction.

New config variables (backend/.env):
  DIARIZATION_ENABLED=false        (set to true to enable)
  DIARIZATION_MAX_SPEAKERS=6       (max auto-detected speakers)
  DIARIZATION_DISTANCE_THRESHOLD=15.0  (tune to merge/split clusters)

How to run/test:
  1. Add DIARIZATION_ENABLED=true to backend/.env
  2. pip install -r requirements.txt  (adds scipy, scikit-learn)
  3. Run backend + frontend normally
  4. Upload a multi-speaker recording, enable "Identify speakers" toggle
  5. Verify transcript view shows colour-coded speaker badges
  6. Generate MOM and verify participants include "Speaker 1", "Speaker 2"
  7. Upload without the toggle — verify plain timestamped view (no regression)

Verification performed:
  - Migration applied cleanly: e5f6a7b8c9d0 -> adds segments_json +
    has_diarization columns to transcripts table
  - Backend code reviewed: apply_diarization() is only called when
    diarize=True is passed; otherwise result dict is returned untouched
  - GET /transcript now always returns segments + has_diarization fields;
    old transcripts return segments=[] and has_diarization=false (backwards
    compatible — TranscriptView renders plain-text fallback for those)

Known issues:
  - MFCC clustering quality is adequate for 2-4 clearly distinct speakers
    in a clean recording. For heavily overlapping speech or noisy audio,
    the speaker labels may be less accurate. This is the expected trade-off
    for a CPU-only, no-token approach.
  - The distance threshold (default 15.0) may need tuning per use case.
    Increase it to merge more clusters (fewer speakers); decrease to split.

[PHASE 15] Background Processing / Job Queue
--------------------------------------------------------------------
Status: COMPLETE
Date: 2026-08-24

What was built:
  MOD  backend/app/core/progress.py
  MOD  backend/app/api/routes/meetings.py
  MOD  backend/app/main.py
  MOD  frontend/src/pages/HomePage.jsx
  MOD  frontend/src/pages/MeetingDetail.jsx

What it does:
  Moves the long-running transcription and MOM generation operations off the
  synchronous request-response cycle into background worker threads.
  
  1. POST /api/meetings/{id}/transcribe:
     - Validates auth, meeting ownership, and audio existence synchronously.
     - Acquires a running lock (`mark_running()`) to prevent duplicate jobs (returns 409).
     - Sets meeting status = "transcribing".
     - Spawns a daemon `threading.Thread` executing `_run_transcribe()` and returns
       immediately with `{"status": "processing", "meeting_id": id}`.
     - Background worker runs FFmpeg -> Whisper -> optional Diarization -> DB persistence,
       updates progress via `set_progress()`, sets status to "transcribed" (or
       "transcription_failed"), and clears progress on completion.
  
  2. POST /api/meetings/{id}/generate-mom:
     - Validates auth and transcript presence synchronously.
     - Acquires `mark_running()` lock.
     - Sets meeting status = "generating_mom".
     - Spawns a daemon `threading.Thread` executing `_run_generate_mom()` and returns
       immediately with `{"status": "processing", "meeting_id": id}`.
     - Background worker runs LLM extraction -> MOM DB row -> ActionItems rows, sets
       status to "mom_generated" (or "mom_generation_failed"), and clears progress.

  3. Progress and Polling:
     - `progress.py` gained `mark_running()`, `is_running()`, and `set_job_error()`.
     - `HomePage.jsx` uses `pollUntilDone()` helper to poll `GET /progress` every 1.5s
       after starting transcription or MOM generation, updating the live progress bar,
       and automatically fetching the final transcript/MOM once completed.
     - `MeetingDetail.jsx` detects in-progress statuses (`transcribing`, `generating_mom`),
       shows a live progress banner with spinner and progress bar, and automatically
       reloads the meeting data upon completion.

Why built this way:
  - Per master prompt Rule: "Use the simplest suitable background mechanism first.
    Do not introduce Redis/Celery or distributed infrastructure unless the project
    actually requires it."
  - Native Python `threading.Thread` runs inside the same process and has direct access
    to `SessionLocal()` and the in-memory `progress` lock.
  - Keeps deployment simple with zero extra services (no Redis broker or worker daemon).
  - Eliminates client-side request timeout risks during long audio processing.

How to run/test:
  1. Start the backend: `uvicorn app.main:app --reload`
  2. Health check: `Invoke-RestMethod http://localhost:8000/api/health`
     -> Returns `"phase": "Phase 15 - Background Processing"`
  3. Upload an audio recording in the UI and click Transcribe -> observe immediate
     non-blocking request and live polling progress bar.
  4. Generate MOM -> observe non-blocking execution with live status banner.
  5. Check Dashboard/MeetingDetail for live in-progress state and auto-refresh.

Verification performed:
  - Import verification: `progress.py`, `meetings.py`, `main.py` all imported cleanly.
  - Health check endpoint verified via PowerShell: returned HTTP 200 with Phase 15.
  - Lock safety: double invocation of `/transcribe` for the same meeting returns 409.

  - Background threads are in-memory to the running Uvicorn process; restarting the

[PHASE 16] Production Security
--------------------------------------------------------------------
Status: COMPLETE

What was built:

What it does:
  Implements multi-layer defensive security across the entire backend:

  1. Rate Limiting (`rate_limiter.py`):
     - In-memory, thread-safe sliding-window rate limiter with zero external dependencies.
     - Protects brute-force vectors: `/register` (5 req/min), `/login` (10 req/min),
       `/forgot-password` (5 req/min), `/reset-password` (5 req/min), `/change-password` (5 req/min).
     - Protects compute-heavy vectors: `/upload` (10 req/min), `/transcribe` (10 req/min),
       `/generate-mom` (10 req/min).
     - Returns HTTP 429 Too Many Requests with standard `Retry-After` header when throttled.

  2. Secure File & Magic Byte Validation (`file_security.py`):
     - Inspects binary container headers on upload:
       - `.wav`: validates `RIFF....WAVE` signature
       - `.mp3`: validates `ID3` tag or MPEG sync word (`0xFF 0xFB/F3/F2`)
       - `.m4a` / `.mp4`: validates ISO `ftyp` box
     - Rejects spoofed/polyglot files (e.g. executable/script renamed to `.mp3`) with HTTP 400.
     - Filename sanitization: strips path separators, directory traversal sequences,
       and control characters.
     - Path safety guard (`safe_path`): strictly verifies path resolution does not escape
       the designated storage boundaries.

  3. HTTP Defensive Security Headers (`main.py`):
     - `X-Content-Type-Options: nosniff`
     - `X-Frame-Options: DENY`
     - `Referrer-Policy: strict-origin-when-cross-origin`
     - `X-XSS-Protection: 1; mode=block`
     - Configurable CORS via `CORS_ORIGINS` in `.env`.

  4. Safe Global Error Handling (`main.py`):
     - Global exception handler intercepts unhandled errors.
     - In production mode (`ENV=production`), prevents internal tracebacks, SQL details,
       or provider errors from leaking to API clients.

  5. Secret Redaction Logging Filter (`logging_config.py`):
     - Automatically scans and redacts Groq keys (`gsk_...`), Gemini keys (`AIzaSy...`),
       JWT bearer tokens, and password fields before writing logs.

Why built this way:
  - In-memory rate limiting and magic byte parsing require zero third-party services,
    preserving fast local execution on Windows 11 / Intel i3 CPU.
  - Follows security-in-depth principles without breaking existing API contracts.

How to run/test:
  1. Automated test suite:
     `python scratch/test_security.py` -> Runs headers, redaction, magic bytes, path safety,
     and rate limit tests.
  2. Health check:
     `GET /api/health` -> returns `"phase": "Phase 16 - Production Security"`.

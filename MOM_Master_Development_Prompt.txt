MOM GENERATOR — MASTER DEVELOPMENT PROMPT

PROJECT PURPOSE
---------------
Build a reliable, modular, industry-relevant AI Minutes of Meeting (MOM) Generator.

Core pipeline:
Upload meeting recording
→ FFmpeg normalization
→ Whisper transcription
→ Database transcript
→ LLM extraction
→ Validated MOMResult
→ MOM + ActionItems database
→ Editable MOM
→ PDF/DOCX export

DEVELOPMENT ENVIRONMENT
-----------------------
- Windows 11
- Python 3.11
- Intel 12th Gen i3 CPU
- No guaranteed GPU
- Prefer free/open-source or low-cost resources
- Backend: FastAPI
- Frontend: React + Vite + Tailwind CSS
- ORM: SQLAlchemy
- Migrations: Alembic
- Development DB: SQLite
- Production DB: PostgreSQL
- STT: faster-whisper
- Audio: FFmpeg
- LLM: Groq by default, through a provider abstraction
- PDF: ReportLab
- DOCX: python-docx

IMPORTANT RELATIONSHIP
----------------------
ActionItem belongs to MOM, not directly to Meeting.

Correct:
Meeting → MOM → ActionItem

Therefore do not keep a Meeting.action_items relationship unless there is a real foreign key from ActionItem to Meeting.

Expected SQLAlchemy relationships:
- Meeting.transcript ↔ Transcript.meeting
- Meeting.mom ↔ MOM.meeting
- MOM.action_items ↔ ActionItem.mom

MOM SERVICE
-----------
mom_service.py owns MOM generation and persistence.

Expected signatures:

generate_mom(db: Session, meeting_id: str, transcript_text: str)

save_mom(db: Session, meeting_id: str, mom: MOMResult)

get_mom(db: Session, meeting_id: str)

Expected flow:

Transcript DB
→ LLM service
→ MOMResult
→ save_mom()
→ MOM row
→ ActionItem rows

Do not duplicate this persistence logic in the API route.

LIST SERIALIZATION
------------------
SQLite Text columns cannot directly store Python lists.

Fields such as:
- participants
- discussion_points
- decisions
- pending_issues

must be serialized before database insertion, normally with:

json.dumps(value, ensure_ascii=False)

When reading them back, deserialize them into Python lists.

Never insert a raw Python list into a SQLite Text column.

GROQ CONFIGURATION
------------------
Groq model selection must come from configuration/environment variables.

Never hardcode the API key.

If Groq returns:
404 model_not_found

verify the currently supported model instead of repeatedly retrying an unavailable model.

Keep model configuration consistent. Do not have conflicting model constants that cause llm_service.py to use a different model from config.py.

ALEMBIC
-------
The migration directory in this project is:

migrations/

not:

alembic/

When creating migrations:
1. Inspect the SQLAlchemy models.
2. Inspect the current DB schema.
3. Run autogenerate.
4. Manually review the generated migration.
5. Apply it.
6. Verify the schema.
7. Test the affected service/API.

SQLite has ALTER TABLE limitations, so Alembic batch operations may be necessary.

Do not blindly stack migrations to compensate for a broken local migration.

PHASE 10 — LONG AUDIO HANDLING
------------------------------
Priority: VERY HIGH

Goal:
Make the application reliable for real-world long meetings.

Target pipeline:

Large Audio
→ FFmpeg
→ validation/normalization
→ audio chunks
→ Whisper per chunk
→ ordered transcript merge
→ transcript DB

Example:
90-minute meeting
→ 9 × 10-minute chunks
→ Whisper
→ merged transcript

Requirements:
- Support long recordings without excessive memory usage.
- Preserve chunk order.
- Handle chunk failures safely.
- Clean temporary chunk files.
- Track processing status/progress.
- Avoid duplicate chunk processing.
- Keep CPU usage practical on the current machine.

Possible statuses:
uploaded
processing_audio
transcribing
transcription_partial
transcribed
failed

Do not add distributed infrastructure prematurely.

DEBUGGING PROTOCOL
------------------
When an endpoint returns a generic 500:

1. Read the complete traceback.
2. Find the deepest/root exception.
3. Identify whether it is:
   - configuration
   - dependency
   - LLM provider
   - schema
   - database
   - migration
   - serialization
   - API routing
   - frontend
4. Reproduce the smallest failing operation.
5. Fix the root cause.
6. Restart backend if code/config changed.
7. Run a direct Python service test.
8. Run the HTTP endpoint test.
9. Verify the database state.
10. Continue only after the current issue is resolved.

Do not hide useful development errors behind generic messages during debugging.
